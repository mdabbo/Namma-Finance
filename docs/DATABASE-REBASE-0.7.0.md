# Database rebase — v0.7.0 (Milestone 7)

## What changed

The development migration chain `0001_initial` … `0024_dashboard_snapshot_audit`
has been consolidated into two files:

| File | Contents |
| --- | --- |
| `0001_baseline.sql` | Complete final schema: tables, indexes, views, triggers, settings bootstrap, expense-category reference rows |
| `0002_seed_reference_data.sql` | Currencies, audit context, version metadata, `PRAGMA user_version` |

Twenty-two intermediate remediation migrations that only existed to repair
development databases were removed. They repaired data that never left a
developer's machine, so there is nothing left for them to fix.

## The old history is preserved

Two annotated git tags hold the complete pre-rebase state:

- **`pre-db-rebase-v0.6.7`** — the exact commit before the rebase, with all 24
  migration files. Use this one to inspect the old chain.
- **`pre-ui-redesign-v0.6.0`** — the earlier pre-redesign preservation point.

```bash
git show pre-db-rebase-v0.6.7:apps/desktop/src-tauri/migrations/0012_audit_log.sql
git checkout pre-db-rebase-v0.6.7   # detached, full old tree
```

## Schema version stays 24

The migration *file* numbers restarted at 1, but the **schema identity is still
24** — `PRAGMA user_version` and `app_metadata.schema_version` both report 24,
and `CURRENT_SCHEMA_VERSION` in `lib.rs` is unchanged.

This is deliberate. Renumbering the schema to 1 would mean two completely
different database shapes both claiming "version 1": the old `0001_initial`
schema and the new baseline. Keeping 24 guarantees that no database in
existence claims a version whose shape differs from what that version means.

## You must delete your development database

**Old development databases are not upgradeable and were never migrated.**

`tauri-plugin-sql` records which migrations ran, with a checksum per version.
An existing database has version 1 recorded with `0001_initial.sql`'s checksum,
which no longer matches `0001_baseline.sql`. The plugin rejects the mismatch and
the app fails to start. This is intentional: it fails loudly rather than
applying a baseline over a populated database.

### How to reset

Delete (or move aside) the database, then start the app — it recreates a clean
database automatically:

```
%APPDATA%\com.mepfinance.app\mep-finance.db
```

```powershell
$root = "$env:APPDATA\com.mepfinance.app"
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$dest  = Join-Path $root "reset-backup-$stamp-db-rebase"
New-Item -ItemType Directory -Path $dest | Out-Null
Move-Item (Join-Path $root "mep-finance.db") (Join-Path $dest "mep-finance.db")
```

Backups under `%APPDATA%\com.mepfinance.app\backups\` were taken from the old
chain. They restore only into a pre-rebase build; treat them as archival.

### Pre-rebase backups are refused, by design

A pre-rebase backup reports `schema_version` 24 — exactly like a rebased
database — so the version number alone cannot tell them apart. What does is the
migration lineage recorded in `_sqlx_migrations`: a rebased database starts with
version 1 `baseline_schema`, an old one with version 1 `initial_schema` and 24
applied migrations.

Restore validation checks that lineage and fails with:

```
BACKUP_PREDATES_DATABASE_REBASE
```

The check runs **before any file is touched**. Without it, restoring an old
backup would replace the live database with a file the migration plugin then
refuses to open — an app that no longer starts. To read such a backup, check out
`pre-db-rebase-v0.6.7` and run that build.

To get data back quickly, use **Load demo workspace** on the empty dashboard
(Milestone 6) — realistic, clearly marked, and removable.

## How the baseline was produced

It was **generated, not hand-written**: the real 24-file chain was replayed into
an in-memory SQLite database and the resulting schema dumped verbatim. A fresh
baseline database was then built and compared against the chain-built one:

- all **259** schema objects identical (tables, indexes, views, triggers),
- reference data identical on every stable column,
- `integrity_check` ok, `foreign_key_check` clean, `user_version` 24,
- zero audit rows on a fresh install.

### Values that must stay per-install

The dump deliberately does **not** freeze values the old chain generated at
install time:

- `expense_categories.sync_uuid` — generated by the same SQL expression the
  `0006` backfill used. Shipping one frozen set would give every office
  identical sync identities.
- `expense_categories.updated_at`, `currencies.updated_at` — stamped at install,
  so FX freshness is never misreported as the moment the baseline was generated.
- `settings.device_id` — generated per install.

Seed rows are inserted **before** the audit triggers are created, matching the
original chain order, so a new workspace starts with an empty audit log.

`test/migrations.test.ts` asserts all of this, including that two independently
created databases share no sync identity.

## Test coverage

The upgrade-path tests were replaced — there is no longer a path to walk. The
financial guarantees they protected are now asserted directly against a freshly
created database: duplicate allocation rejection, approved-revision immutability,
append-only audit log, payment/contract date validation, due-date confirmation,
recoverable data-quality issues, backup-path redaction, and document hash
validation.
